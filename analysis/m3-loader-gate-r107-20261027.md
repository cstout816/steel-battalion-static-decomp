# Steel Battalion loader gate trace — r105d/e, r106, and r107

## Result

The new-pilot route reached the visible `NOW LOADING` screen in r107. The first mission frame was not reached. The first repeatable blocker supported by this trace is the guest loader-state gate: guest site `0x00101FC0` requests mode 1 but receives helper result 0, so it skips the mode-1 scheduler and leaves active mode 0, load index 1, and load stage 0. Its helper callback is passed a null object. The later mode-2 scan returns zero with an unchanged pair on every pass.

This identifies the stalled stage, but not the earlier operation that made the loader object null. No behavior fix or seed is justified yet. The `TEX00.BIN` cache miss is a separate candidate; the source-side asset exists and had a successful open, so the cache miss alone is not established as the cause. Rendering is very slow, but the graphics/event counters continue to advance and do not explain the mode-1 gate result.

## Loader state and control flow

At tick `375028750`, guest caller `0x000E0109` ran `sub_0001DAA0` in requested mode 0 and stored `0x48000078` in global `0x00311CC8`. This is the sole direct absolute store to `0x00311CC8` found by searching the generated C source.

At tick `375427859`, the later callback path from `sub_0001DAA0` passed its current `MEM32(0x00311CC8)` value as the object argument to `sub_00191451`; the trace recorded that argument as 0. `sub_00191451` called the function pointer in guest global `0x0025D188` (`0xFE0000A8`) with context `0x00740040`. It returned 0, the object-valid byte was 0, and the selected state became `0x103`; the second callback target was `0xFE0000A0` from `0x0025D180`. These synthetic kernel targets are in the validated 123-entry bridged table; no missing indirect target was seeded.

The callback’s null object and the prior nonzero initialization are separated by roughly 399 seconds. The intervening clear/reset operation is not observed. The r105d/e/r106 guest page-watch probe captured only the initial write and the runs crashed with the same native access violation; it is not a safe basis for another behavioral conclusion.

Across 175 emitted scheduler-gate records at `0x00101FC0`, the values were `requested_mode=1`, `helper_result=0`, `decision=skip`, `active_mode=0`, `load_index=1`, `load_stage=0`, and `object=0x2B`. The recurring mode-2 pass at `sub_000C3020` returned at `0x000C32D6` with `range=2..11`, `last_index=28`, `branch=scan`, `result=0`, and pair `0x011E2E00/0`. At its special index `0x1E`, `sub_000C2EB0` returned raw EAX `0xFFFF0001`; the pair remained unchanged. There were 175 pair-output and pass-output records, and 700 state-callback rows.

The generated callback trace limit is 2,048; load pass and pair-output traces each stop at 8,192. r107 emitted 175 of each, so these limits were not hit. File lifecycle tracing emitted 9,446 opens and 9,218 closes with zero open-cap marker. The failed-path trace emitted 64 rows and reached its 64-row cap; later failed paths may therefore be absent. Menu object-gate tracing emitted 512 rows and reached its cap. Marker counts are complete despite these per-marker limits; the asynchronous relay dropped zero lines.

## File completion and the `TEX00.BIN` candidate

r107 emitted 5,354 `[READ]` records. Host/IOS read status was successful; 24 guest return values were `STATUS_PENDING` (`0x103`) on handles marked asynchronous. This is the configured compatibility contract: `bridge_NtReadFile` executes the host read synchronously, writes the I/O status block and calls `bridge_complete_file_io` before returning guest `STATUS_PENDING`. Those rows are not evidence of outstanding reads. In all-read mode, the trace emits every row through 30,000 then samples every 1,000; r107 stayed below that threshold.

The first source-side probe for `D:\media\BIN\TEX00.BIN` succeeded at tick `375427843`; the local extracted asset is 702,976 bytes at `iso/local-analysis/game_files/Media/BIN/TEX00.bin`. In the repeated mode-2 special-index path, `Z:\TEX00.BIN` under the save cache returns `STATUS_OBJECT_NAME_NOT_FOUND` (`0xC0000034`) and the helper returns `0xFFFF0001`. No source path is opened in that same special-index subcall. However, the earlier source probe succeeded, the source asset exists, and other asset reads complete. This leaves the missing cache copy as a candidate requiring producer/copy-path correlation; it is not a supported root cause.

The loader thread’s sampled stack around guest `0x000C319A` shows the current scan inputs and filename buffer (including `Z:\STRM01.WAV`); lifecycle records show paired cache/source asset probes such as `STRM00.WAV`, `STRM01.WAV`, `SOUND.BIN`, and `TEXOBJ.BIN` succeeding. There is no read error or uncompleted file request tied to the mode-1 gate.

## Graphics and synchronization, kept separate

r107 emitted 14,073 DCF4 callback rows and 244 NV2A tick rows. DCF4 callbacks and resets continued; sampled `DMA_PUT` and `DMA_GET` matched, while frame, counter, target, and semaphore values advanced. No distinct unsignaled DCF4 wait reproduced, so DCF4 producer-stage tracing was not enabled. This run does not support a graphics-event deadlock as the loading cause.

The trace emitted 347 raster-performance windows. The recurring loading-frame workload was 27 batches over 56 triangles, with samples around 2.0–2.15 seconds batch wall time and 7.8–8.3 seconds aggregate active time over four raster workers. This confirms severe rendering cost and can explain a long loading slowdown. It does not explain why the independent guest mode-1 gate keeps returning helper result 0. The first mission frame and frame pacing after mission entry remain unverified.
