# Graphics Backend Decision Record

**Status:** Native Direct3D 12 selected as the Windows NV2A backend; direct D3D12-versus-Vulkan Steel Battalion performance is not measured
**Current milestone:** Milestone 3, Boot and Compatibility
**Static recompilation architecture:** Retained. The options below change only how translated NV2A rendering is produced; none replaces the project with full-system emulation.

## Evidence from the current build

- The observed Steel Battalion startup workload writes NV2A pushbuffers. The runtime scan routes decoded methods into `nv2a_pb_exec_method()` and its partial CPU rasterizer.
- A clean, untraced 90-second run remained on the CAPCOM splash, reported 27 flips and about 0.44 guest FPS near the end, and measured about 16 million pixel writes across the captured period.
- A temporary timing probe measured 2.18–2.40 seconds inside `raster_batch()` for each sampled splash frame after the initial frame. The instrumented source was restored and the clean Release target rebuilt.
- The runtime already contains a Windows D3D8 compatibility layer backed by D3D11, an NV2A vertex-microcode-to-HLSL compiler in `src/d3d/d3d8_vsh.c`, and a combiner-to-HLSL path in `src/d3d/d3d8_combiners.c`.
- The standalone `src/nv2a/nv2a_pgraph_d3d11.c` translator is not wired to the normal pushbuffer path. It assumes five-word screen-space vertices and an optional fixed texture lookup for a reference menu. It cannot accept the observed game path as-is.
- In the captured startup run, the executor reported 52 vertex-program batches / 208 vertices and attributes in slots `v0`–`v15`. It observed texture state in 51 batches, but reported no batches with a usable texture stage; successful texture sampling is not established.
- No renderer option has reached title-screen parity, and no runtime option is validated for Steel Battalion gameplay.

## Recommended decision

**Select native Direct3D 12 as the primary NV2A backend for this Windows-only target and RTX 4070 SUPER.** No public matched Steel Battalion capture compares D3D12 and Vulkan, so this is a best-supported performance architecture choice, not a measured API-level win. A native D3D12 renderer for original Xbox XBE recompilation is already documented by [XboxXBERecomp](https://github.com/TGP482/XboxXBERecomp), which translates NV2A programs and fixed-function state to HLSL and renders on a dedicated thread. That is a closer platform match than porting xemu's Vulkan subsystem, which is coupled to QEMU/PGRAPH services and has unresolved license/dependency closure in this project. Vulkan has no demonstrated performance advantage here: xemu community comparisons report mixed Vulkan/OpenGL results (including games where OpenGL is faster), and none compares D3D12. D3D12 is therefore the chosen path unless a same-scene D3D12/Vulkan benchmark later demonstrates a Vulkan win. The local D3D12 prototype is only a correctness experiment with synchronous full-surface transfers; it is not yet the performance architecture. The measured software bottleneck is 2.18–2.40 seconds in `raster_batch()` per sampled splash frame, so the implementation must replace CPU pixel work and avoid CPU/GPU synchronization.

The current XboxRecomp foundation documents D3D8-to-D3D11 on Windows, so its existing backend is not a ready D3D12 NV2A renderer. The separate [XboxXBERecomp](https://github.com/TGP482/XboxXBERecomp) project documents a native D3D12 renderer and an MIT repository license; any code reuse still requires file-level license, third-party, and suitability review. The xemu Vulkan route has a mature NV2A implementation, but our source audit found a GPL-2-or-later PGRAPH header dependency and additional unresolved dependency licensing. Do not import it unless the user later chooses a compatible license route. In all cases the static-recompiled CPU and kernel architecture remains unchanged, and no emulator process is part of the runtime.

The community [Xemu-SB-VK fork](https://github.com/quizerno/Xemu-SB-VK) reports that original Steel Battalion performance varies between users and campaigns; it does not publish an API comparison. xemu issue [#1838](https://github.com/xemu-project/xemu/issues/1838) records mixed Vulkan-versus-OpenGL game results on an NVIDIA RTX 3080, so Vulkan cannot be assumed faster for this workload. Direct D3D12-versus-Vulkan speed remains **unverified**. If a Vulkan alternative is later made legally and technically comparable, benchmark both on identical 640×480 guest captures and representative campaign scenes before claiming a measured winner.

The local D3D12 prototype remains a correctness/reference experiment, not the production renderer. It verifies a synthetic triangle and byte-identical output for two synchronized startup passes (opaque-black depth pass and following transparent textured pass), but no visible texture, title-screen parity, or speedup. The chosen production design must batch NV2A state/draw work into D3D12 command lists, use asynchronous resource uploads, and avoid readback in the frame loop. D3D11 stays a compatibility/interim path only.

The local Vulkan runtime probe (`vulkaninfo --summary`) reports Vulkan instance 1.4.341 and an NVIDIA GeForce RTX 4070 SUPER on driver 617.42 / device API 1.4.351. The driver reports `VK_EXT_fragment_shader_interlock`, `VK_EXT_custom_border_color`, `VK_EXT_external_memory_host`, and `VK_KHR_dynamic_rendering`, all useful capabilities for a legacy ordered-pixel renderer. This establishes that the target machine exposes Vulkan and relevant extensions; it does not verify that an adapted renderer initializes, renders correctly, or outperforms D3D12. `VULKAN_SDK` and development headers are not installed/configured, so a project-local, license-reviewed header/build dependency source is still needed; no system dependency was installed.

This is not a drop-in renderer library. The renderer API takes xemu `NV2AState`/`PGRAPHState`, uses QEMU helpers and memory-region services, includes xemu shader/surface/texture state, and its `renderer.c` initializes an offscreen GL context for optional external-memory sharing. The checked-out XboxRecomp state structure is explicitly a minimal PGRAPH stub, and its current integrated backend is a narrow D3D11 method handler. Integrating Vulkan therefore requires either expanding the local guest GPU state model and writing a host-facing adapter, or isolating/adapting the renderer behind a smaller API; it does not require adopting QEMU's CPU, kernel, or machine-emulation loop. This is substantial work but not a technical dead end. Keep the choice provisional until the adapter can consume the real Steel Battalion pushbuffer state and pass the software-reference frame checks.

#### Historical Vulkan integration proposal (superseded by native D3D12 choice)

Use xemu's existing LGPL PGRAPH method/state model together with its Vulkan renderer, adapting the NV2A GPU subsystem to XboxRecomp's guest-memory and pushbuffer runtime. Do not build a parallel, reduced Vulkan rasterizer around the prototype's `s_gpu` packet: a second state/texture/shader implementation would duplicate the hardest correctness work and is a poor fit for complete campaign support. Retain the statically recompiled x86 game and Xbox kernel/audio/input layers; exclude xemu's CPU, machine, PFIFO thread, and full-system boot loop. The current `nv2a_pb_exec` pushbuffer front-end should supply command words to the adapted PGRAPH method processor, while the PGRAPH implementation owns complete GPU register, surface, texture, draw, and synchronization state. Keep the CPU raster as the differential reference until each exercised operation has parity.

The target API boundary will replace xemu's QEMU-specific utilities and external-GL interop with XboxRecomp/platform services. It must preserve the guest command packet semantics, RAM aliases, texture cache invalidation, surface coherency, vertex/index data, combiner and shader translation, depth/blend/order behavior, report/flip synchronization, and window presentation. No per-triangle full-surface readback. The startup/logo path is the first boot gate, but implementation must grow through the real PGRAPH state model rather than stopping at a synthetic triangle.

The Vulkan device feature requirements in xemu's `instance.c` include `depthClamp`, `fillModeNonSolid`, `geometryShader`, `occlusionQueryPrecise`, `shaderClipDistance`, and `shaderTessellationAndGeometryPointSize`. A local `vulkaninfo` probe reported all six as supported on the RTX 4070 SUPER. This confirms the target GPU meets that basic feature gate, not that the renderer has initialized or that game frames match. The Vulkan integration and license route below are retained as research history; they are not the current implementation plan.

### Native D3D12 reuse feasibility audit

Read-only source review of [XboxXBERecomp](https://github.com/TGP482/XboxXBERecomp) `main` found a native renderer in `runtime/gpu/d3d12.cpp` (about 140 KB / 3,304 lines), with shared `gpu::Backend`, `gpu::State`, shader, texture, and vertex interfaces. Its state represents the XDK D3D8 API; the backend handles clears, draws, copies, four texture stages, programmable and fixed-function shaders, and resource synchronization. The repository is MIT-licensed. Its `THIRD_PARTY.txt` identifies toml++ and Dear ImGui (MIT) and SDL 3 (zlib-style license); any reuse must retain applicable notices and audit the compiled dependency closure. The renderer also depends on that project's app/window, diagnostics, and kernel interfaces, so the source is not a self-contained drop-in.

The local XboxRecomp foundation has a separate D3D8-to-D3D11 implementation. Its `dev_BeginPush` and `dev_EndPush` return `E_NOTIMPL`, while Steel Battalion's observed graphics workload enters the separate low-level NV2A pushbuffer executor (`nv2a_pb_exec`). Therefore XboxXBERecomp's D3D12 D3D8 backend does not, by itself, cover the raw NV2A packet path seen during this title's startup. Switching the entire foundation would be a material recompiler/runtime change and would still leave that pushbuffer gap, so the selected XboxRecomp static-recompilation base remains. Implement the D3D12 renderer at the project's actual PGRAPH draw/state boundary; use the upstream renderer as a behavior and resource-management reference where the interfaces and licenses fit. First trace which game D3D8 entry points and raw PGRAPH packets feed each observed splash draw.

No upstream code was copied, no dependency was added, and no local source or build changed during this audit. It narrows the next task to the D3D8/PGRAPH boundary; it does not verify D3D12 title rendering or speed.

### File-level license and Windows build-input audit (2026-10-18)

This narrows the earlier license conclusion. xemu as a complete program is GPL-2, while the examined PGRAPH core files (`pgraph.c`, `pgraph.h`, and `texture.c`) and Vulkan renderer files carry their own LGPL-2.1-or-later notices. Do not treat the full xemu tree as LGPL, and do not copy files solely because they are next to LGPL files. The prospective graphics port must keep an exact source manifest and audit every copied implementation, header, shader, helper, and generated artifact at pinned commit `8fc3208`; the required corresponding source and modification notices must travel with any binary. The local XboxRecomp contribution policy expressly excludes GPL-derived code and currently documents only the APU sources and `nv2a_regs.h` as LGPL exceptions. No xemu PGRAPH source has been copied. The project has no approved distribution license yet.

The upstream PGRAPH build lists seven shared PGRAPH translation units (`pgraph.c`, `profile.c`, `rdi.c`, `s3tc.c`, `swizzle.c`, `texture.c`, `vertex.c`), the xemu vertex-shader CPU module, and 17 Vulkan files. The method entry point accepts `NV2AState`, subchannel, method, first parameter, the full packet parameter array, available/lookahead word counts, and increment mode. Our packet-boundary patch now carries the packet array/count/increment mode to one adapter entry while preserving current method-by-method execution. A direct port still needs an XboxRecomp-owned replacement for QEMU locking/events, memory-region/DMA mapping, error/logging/allocation helpers, renderer flip/display hooks, and the PFIFO callback contract. It must not import the PFIFO worker or full emulator loop. The Vulkan `renderer.c` also has optional external-GL interop; for this Windows target that path should be disabled or replaced with the application's presentation service.

Windows build-input findings: this machine has `Windows System32 Vulkan loader` and `vulkaninfo.exe`, but no `VULKAN_SDK` environment setting, Vulkan development headers, `glslangValidator`, or `glslc` was found. Vulkan-Headers files are Apache-2.0 OR MIT. Volk is MIT, is C89/Windows-compatible, and supports runtime function loading; using it avoids a project dependency on the Vulkan SDK import library. The driver-installed Vulkan loader can be resolved at runtime, so headers/Volk can be project-local. Xemu's renderer also directly builds VMA, SPIRV-Reflect, and glslang. VMA is MIT; SPIRV-Reflect is Apache-2.0; glslang is mixed-license and its current upstream build needs C++17. The local XboxRecomp top-level CMake currently enables only C, so integrating VMA/glslang requires either a deliberate C++ build-language change or a separately-built C++ dependency target. The exact glslang component and transitive SPIR-V build closure at the pinned xemu revision remains unaudited; no dependencies have been installed or downloaded.

**Next implementation gate:** finish the pinned-revision per-file and transitive license manifest, then decide whether this project will carry an isolated LGPL Vulkan/PGRAPH library and the corresponding-source/relink package, or independently implement the API bridge around licensed interfaces. This is a distribution and build design choice, not permission to switch to full-system emulation. Until it is resolved, keep the project patch-only boundary, static-recompiled CPU, software reference, milestone status, and all progress bars unchanged.

### GPL dependency found in the PGRAPH reuse path (2026-10-18)

A deeper source-closure check found a GPL dependency missed by the earlier file-level scan: LGPL `pgraph.h` includes `pgraph/vsh_regs.h`, whose header explicitly offers GPL version 2 or version 3. The LGPL `pgraph.c` includes `nv2a_int.h`, and through the PGRAPH state definitions it requires that GPL header. The PGRAPH method implementation therefore cannot be treated as an independently reusable LGPL-only component without replacing the GPL-dependent declarations/implementation. This matches the local XboxRecomp contribution policy, which says not to port GPL-derived code. None of these xemu files has been copied into the project.

This invalidates the previous assumption that the full xemu PGRAPH method/state model could be adopted while keeping a permissive project license. This historical research note had left both Vulkan reuse and the license route unresolved. The decision is now resolved for the current Windows target: use a native D3D12 NV2A backend and do not port the xemu Vulkan PGRAPH stack. The D3D12 choice avoids relying on the unresolved xemu license/dependency closure, while direct performance superiority over Vulkan remains unmeasured. The earlier alternatives are retained below as research history, not as pending approval:

1. **GPL-compatible project:** permit a GPL-2-or-later application/runtime and integrate the GPL PGRAPH/VSH path with the LGPL Vulkan renderer, while auditing every dependency and complying with corresponding-source and relinking obligations. This requires maintaining a project-local runtime integration rather than contributing GPL-derived changes upstream to XboxRecomp.
2. **Keep the project permissive:** do not use `vsh_regs.h` or GPL-derived PGRAPH implementation. Build an independently implemented PGRAPH state/method layer around the LGPL Vulkan renderer and the project's existing code, using hardware behavior/specifications as references. This is a substantially larger correctness effort than the previously selected upstream state-model reuse route.

Both options preserve static recompilation and omit xemu's CPU/full-machine loop. The project currently has no root LICENSE file or approved distribution license, and no GPL code has been copied. Neither route is selected. No title screen, Vulkan renderer boot, parity, audio, campaign, or direct API performance comparison has been verified. Keep Milestone 3 and all progress bars unchanged.

### License route refined after Apache-2.0 compatibility check (2026-10-18)

The license choice is now more specific. Xemu's Vulkan build includes SPIRV-Reflect, whose pinned component is Apache-2.0; Apache-2.0 is incompatible with GPL-2-only, while GPL-3 is compatible. The PGRAPH `vsh_regs.h` header allows choosing GPLv2 or GPLv3, so a reuse-heavy route would need to select GPLv3 for that code and provide the complete GPL/LGPL source, notices, and relinkable library/object artifacts as required. The project may be able to use a GPL-3.0-or-later distribution license for that route, but the full dependency closure still needs review; this is not a final legal approval. Do not choose GPL-2.0-only for an integrated build that includes Apache-2.0 SPIRV-Reflect.

The choices to present are: (1) choose a GPL-3.0-or-later project distribution and continue the xemu PGRAPH/Vulkan reuse after completing the manifest and packaging/relink audit; (2) keep a permissive project and implement an independent PGRAPH/VSH state and method layer around Vulkan, avoiding GPL source; or (3) if GPL-2.0-or-later specifically is required, replace or avoid Apache-2.0-only components such as SPIRV-Reflect and audit every remaining dependency before proceeding. All choices retain static recompilation and exclude xemu's full system/CPU loop. This changes the distribution license or substantially changes graphics implementation scope, so wait for the user's choice.

### Remaining shader-compiler license closure (2026-10-18)

The pinned xemu Meson configuration narrows glslang's build: it disables HLSL and SPIR-V optimizer support, and links `glslang`, `MachineIndependent`, `GenericCodeGen`, and `SPIRV`. This avoids the HLSL component and the separate SPIRV-Tools optimizer dependency. Runtime GLSL preprocessing is still part of glslang, however. The exact pinned `glslang` `LICENSE.txt` says its preprocessor carries extra license terms, including NVIDIA's 2002 software license, in addition to core glslang terms. The compatibility of that preprocessor license with a GPL-3.0-or-later application has not been established. Therefore the previous GPL-3 option resolves the Apache-2.0/SPIRV-Reflect conflict in principle, but it does **not** yet clear the complete shader compiler license closure.

The permissive alternative is also more concrete than a full rewrite from zero: the local XboxRecomp runtime already has its own partial `pgraph_method` state tracker and CPU transform/combiner/texture raster path, but its PGRAPH struct is explicitly a stub and the renderer is incomplete. It could be extended independently, while reusing only separately audited compatible Vulkan and shader components. That requires implementing the missing method/state semantics and validating them against real guest captures; current startup/render evidence is insufficient to size or guarantee that route.

### Backend decision reaffirmed after performance research (2026-10-18)

The user requested the best-performing native NV2A backend for Windows 10/11 on an RTX 4070 SUPER. Research found no matched Steel Battalion D3D12-versus-Vulkan benchmark and no reliable evidence that either API is universally faster on NVIDIA. NVIDIA supports both APIs on GeForce RTX; API support alone is not a performance result. The closest available title-specific evidence is that the Steel Battalion Vulkan fork is a full xemu-based emulator, which is outside this project's static-recompilation requirement. xemu's Vulkan NV2A code is mature, but its port has substantial QEMU/PGRAPH integration work and the dependency/license issues above. A separate original-Xbox recompilation project documents a native D3D12 NV2A renderer, but it accepts a higher-level D3D8 state interface and does not directly implement this project's raw pushbuffer path.

**Decision: keep native D3D12 as the primary NV2A API for this Windows-only project.** This is the best-supported performance implementation path under the project's platform and architecture constraints: it avoids the substantial xemu Vulkan subsystem port and has a native original-Xbox recompilation renderer to guide the design. It is not a claim that D3D12 is intrinsically faster than Vulkan. No D3D12-versus-Vulkan Steel Battalion measurement exists. The current local D3D12 prototype remains experimental; its synchronous surface transfers are not performance-ready, and its ~0.4 FPS startup splash runs show no measured improvement. Continue with GPU-resident resources and batched D3D12 command submission, compare against identical software-reference frames, and revisit Vulkan only if a legally and technically comparable same-scene benchmark demonstrates better frame time or frame pacing. Milestone 3 and progress bars remain unchanged.
