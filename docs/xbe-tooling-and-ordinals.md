# XBE inspection and Ghidra support

## Findings

- The local Ghidra 12.1.4 workspace already includes the XboxDev `ghidra-xbe` extension and its XbSymbolDatabase integration. This is the preferred path for importing and analyzing the original-Xbox XBE. The portable Java annotator, verifier, candidate CSV, and upstream license notice are in [`tools/reverse-engineering/xbox-kernel-ordinals/`](../tools/reverse-engineering/xbox-kernel-ordinals/README.md) and were installed in the active Ghidra script workspace.
- Upstream review confirms XbSymbolDatabase is an MIT-licensed OOVPA pattern-signature library, and `ghidra-xbe` uses it for library-symbol recovery. This is a complementary source for recognizing compiled XDK/library routines in the XBE; it is not a verified build-4627 ordinal-name table. Keep its matches separate from the provisional ordinal CSV and verify recovered names against code and call sites. No XbSymbolDatabase or Ghidra extension code was copied into this repository.
- The supplied Steel Battalion executable is a retail `XBEH` image; the local parser reports XDK library build 4627 and 123 distinct kernel thunk imports. All 123 ordinals occur in the current xboxrecomp candidate map. That map's own notes say it is cross-checked against kernel builds 3944 and 4039, so the Ghidra labels remain explicitly provisional for this build.
- Cxbx-Reloaded contains an XBE metadata printer and loader checks for XBE signatures and section integrity. Those are useful independent metadata checks. Cxbx-Reloaded is an emulator, so running it does not create or validate this project's statically recompiled Windows executable.
- Exact-name public-source searches did not verify a project named **XbeTripper** or **xberewrite**. Do not base the pipeline on either name until a repository or project URL is supplied and its source/licensing can be reviewed. A different, verifiable project named [XboxXBERecomp](https://github.com/TGP482/XboxXBERecomp) exists; do not assume it is the same tool the names refer to.
- A possible name collision is [XboxDev/extract-xiso](https://github.com/XboxDev/extract-xiso): its documented `-r` mode rewrites an XISO filesystem and may patch XBE media flags. It operates on the disc image layout; it does not lift XBE machine code, create a native Windows executable, or serve as an XBE runner. Its upstream `LICENSE.TXT` has a BSD-style license with attribution/advertising conditions, so it should not be bundled without a separate license review. No extract-xiso code or binary was added.
- XboxXBERecomp is a separate MIT-licensed AOT framework. Its upstream README describes translating XBE x86 code ahead of time into a native 64-bit Windows executable, implementing Xbox kernel/XDK APIs, and rendering through D3D12. Its `xbe_symbols` setup requires a matching `xdk/<build>/signatures.toml` and game-specific configuration/hooks. Whether upstream currently has a signature package for this game's XDK 4627 build has not been verified. This is a legitimate alternative to evaluate, not an emulator, but it is not adopted here: this project already builds XboxRecomp AOT output and has a Steel Battalion-specific runtime plus current screen-gated loading evidence. Migrating would be a major architecture change that must be compared against the exact XDK 4627 image and preserved runtime behavior before approval; no such evidence currently justifies it.
- Cxbx-Reloaded's own README identifies it as an original-Xbox emulator and its repository is GPL-2.0. Its XBE metadata and loader code can inform read-only format validation, but launching the game in Cxbx would not advance or verify the native AOT executable. No Cxbx code has been incorporated.
- Primary-source recheck: Cxbx-Reloaded's README calls it an emulator; it documents the XBE dump and exposes a metadata/signature/integrity path, but this is not a static-recompilation runner. `extract-xiso`'s README describes `-r` as rewriting an XISO filesystem. Neither tool replaces the project's existing AOT executable path.

## Why this is not an executable patch

The Ghidra script labels existing kernel thunk cells and never modifies the XBE. No custom hooks or cave are needed for this step. Any future hook proposal must first prove a specific need and must be reviewed against the XBE section table, mapped section bounds, alignment, and code/data references. A zero/NOP byte run alone is not proof that bytes are unused. Prefer a separately added, correctly aligned PE section for host-side instrumentation; do not patch user game bytes without a separate, reviewed design.
